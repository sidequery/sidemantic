# Remaining official Ossie converter surfaces versus Sidemantic

Research snapshot: Apache `ossie-converters` HEAD **011ea9f9a1e2c941f351e18e071622339ccae881**, local checkout `/workspace/ossie-converters-research`; Sidemantic HEAD **a7df3c9eae7c1a9a916ebe317ee378408d7d721b** plus current working tree. Source/test inspection only; no converter tests executed or product files modified. All nine directories below contain implementations in the Apache-hosted repository, not merely roadmap entries. OrionBelt additionally identifies an external canonical development/publishing repository.

Arrows below describe file/model conversion directions, not live warehouse execution. Every named native surface in this matrix is absent from Sidemantic's registered formats ([local registry](/workspace/sidemantic/sidemantic/formats.py:66)). Its generic Ossie document preservation does not implement those vendor conversions. Its Tableau adapter reads `.tds/.twb/.tdsx/.twbx` ([source](/workspace/sidemantic/sidemantic/adapters/tableau.py:1)), a different surface from Salesforce Semantic Model JSON/Tableau Next.

| Official project | Implemented surface and direction | Fidelity / important boundaries | Dependencies and Sidemantic comparison |
|---|---|---|---|
| **ontology** | Ossie ontology spec YAML/Pydantic DTOs ↔ in-memory `OssieOntology` model. Parses derived/required formulas and mapping expressions into ASTs; supplies ontology reasoner/model tooling. This is shared ontology infrastructure, not another vendor spoke. | Real semantic object construction, concept/relationship/mapping resolution, formula parsing; structure and YAML snapshot corpus tests. Do not count its two internal converters as two external formats. | Python ≥3.11, Pydantic, PLY, PyYAML; local/offline. Sidemantic instead preserves/serializes ontology documents and performs static checks, without ontology execution/reasoning/model lowering. [O1–O2] |
| **NVIDIA Auto Ontology** | Native model-document YAML ↔ Ossie core semantic model; native → separate Ossie ontology **and standalone mapping** documents; optional embedded ontology variant. Formerly GSF, same surface rather than an extra converter. | Datasets→catalog table terms, columns/computed fields, custom-analysis metrics, joins/FKs; full native snapshot extension retains IDs, catalog-only metadata and native SQL. Export from arbitrary Ossie loses AI context/dimensions/synonyms/extensions. Exactly one represented table per native term; cross-database SQL objects rejected. Ontology path declares concepts without keys but cannot map them; fields without portable types omitted. | Python ≥3.11, PyYAML + sqlglot; offline, no NVIDIA instance required. Genuine Sidemantic import/export and ontology-generation gap. [N1–N3] |
| **RelationalAI** | Ossie ontology → in-memory PyRel `OntologyModel`, serializable to PyRel source. **Export only**, no PyRel importer. | Concepts, identities, relationships, mappings and parsed formulas become PyRel constructs. Row-field SQL accepts scalar subset; functions, CASE, CAST and qualified columns rejected. Raw/unparsed formulas skipped. Source compilation tests are not live engine execution. | Python ≥3.11 + ontology package; functioning converter requires optional `relationalai==1.39.0` proprietary SDK and config. Default `warehouse_table` reads warehouse metadata; `declared_table` enables offline conversion/compilation. Running generated code requires configured RelationalAI/Snowflake service. Sidemantic has no ontology→PyRel surface. [R1–R3] |
| **Palantir** | Extracted ontology JSON + `data_sets/*.json`, or ZIP → Ossie ontology with embedded logical model and mappings. **Import only**, no Palantir export. Can chain through ontology package to YAML and optionally RelationalAI. | Converts object/property/relationship structure, keys, status-policy hooks, multi-dataset mappings, inferred PK→PK inheritance. Missing identifying fields skip concept mapping; array-valued property mapping skipped with warning. Not proof of arbitrary Foundry asset/action portability. | Python ≥3.11 + ontology package; offline exported files, no Palantir client/service dependency. Optional downstream RelationalAI chain has separate SDK requirement. Genuine Sidemantic ontology import gap. [P1–P3] |
| **Salesforce** | Salesforce Semantic Model JSON ↔ Ossie YAML (Data Cloud/Tableau Next Tua model). | Preserves unmapped Salesforce properties in extensions. SQL/TABLEAU metric expression validation and Tua generation; unsupported calculated field dialects omitted with warnings; formula/semantic-field relationships preserved only as extensions. No universal “lossless” semantic conversion: arbitrary Ossie time types and computed fields have direction-specific limits. Published Salesforce schema can reject API-valid `Dmo` models. | Java 21+, Maven build, bundled Ossie schema; Salesforce JSON schema must be obtained separately for validation, schema-dependent tests can otherwise skip. No live Salesforce account needed for file conversion. Sidemantic Tableau XML support is distinct and does not close this gap. [S1–S3] |
| **Sigma** | Sigma Data Model code-representation JSON (`/v2/dataModels/{id}/spec`) ↔ Ossie YAML. | Native IDs/formulas and unmodeled presentation/governance/source blocks preserved. Sigma formula parser↔sqlglot; `SIGMA` expression always retained, ANSI only on successful translation. Unsupported output formula columns/metrics omitted with issues; foreign-origin cross-dataset metrics dropped; only warehouse-table sources become portable sources, derived sources only native extension + marker. Two native fixture round trips compare normalized structures, not actual original bytes. | Python ≥3.11, Apache Ossie package + PyYAML + sqlglot. Offline conversion; sigcli/API only needed to obtain/apply native files. Genuine Sidemantic missing native format. [G1–G3] |
| **OrionBelt/OBML** | OBML ↔ Ossie core model; additionally OBML → Ossie ontology (embedded model/mapping), **no ontology reverse converter**. | Core metrics translate filters, totals, windows/cumulative calculations when faithful; unsupported semantics retained in extensions with warnings. Foreign extensions and unconvertible Ossie metrics round-trip, but preserved metrics are not queryable in OBML. Ontology path is narrower: skips many-to-many; no column-level value concepts/metrics; first PK column only for composite keys, falls back to first column when no PK. | Python ≥3.12 + PyYAML/jsonschema/referencing/sqlglot; optional full OrionBelt engine only for deeper OBML validation. Apache-hosted copy, but README names `ralfbecher/orionbelt-semantic-layer/packages/ossie-orionbelt` as canonical/publishing source. Genuine Sidemantic native-format and ontology-generation gaps. [B1–B3] |
| **Wisdom** | WisdomAI domain-export JSON format `1.0` ↔ Ossie core model. | Fields/formulas/measures, model instructions/knowledge, composite equality joins; cardinality encoded using exact AI-context notes. OR joins dropped; many-to-many warns; export drops unique keys/extensions and field/metric AI context + synonyms/examples. Deterministic connection placeholders must be remapped on import; unresolved metric placement falls back to first dataset. | Python ≥3.11 + Apache Ossie/PyYAML; offline files. Missing Sidemantic native format; not general knowledge/security/reviewed-query portability. [W1–W2] |
| **wisdom-semantic-view** | Snowflake semantic-view YAML ↔ Ossie ↔ Wisdom format-1.0 JSON, with optional enrichment; four internal conversion functions and two pipeline CLIs. | **Explicit finance-fixture-only implementation**, not general Snowflake/Wisdom interoperability. Only bare-column expressions or exact `SUM(bookings.amount)`; metric references must be `bookings`; restricted keys/types/one relationship. Preserves fixture metric synonyms + `sql_generation` instructions through knowledge items. Golden round-trip tests exercise finance fixture. | Python ≥3.11 + PyYAML only; no accounts/network, deliberately independent of `snowflake` and `wisdom` converters. Missing exact pipeline in Sidemantic but should not be weighted as another broad vendor gap; Sidemantic Snowflake work is a separate comparison. [V1–V3] |

## Sidemantic boundary evidence and practical priorities

- [Ontology capability documentation](/workspace/sidemantic/docs/compatibility/ossie.md:325) explicitly says static checks/source preservation only, no reasoning or runtime conversion; [lowering regression test](/workspace/sidemantic/tests/interchange/ossie/test_lowering.py:606) asserts no executable catalog for ontology. [Exact/canonical source round-trip documentation](/workspace/sidemantic/docs/compatibility/ossie.md:346) is a preservation claim, not semantic migration.
- For broad additional native semantic-model coverage, **Sigma, Salesforce Semantic Model, OBML, NVIDIA, Wisdom** are concrete missing adapters. Existing Ossie bridge may make official converters usable as external preprocessing/postprocessing, but that is integration potential, not present native support or verified end-to-end fidelity.
- **Palantir and RelationalAI** require an explicit ontology roadmap/architecture decision; treating them as ordinary SQL-model adapters would lose their concept/rule/identity semantics. NVIDIA/OBML ontology generation likewise exceeds opaque ontology retention.
- **ontology** and **wisdom-semantic-view** should be separated in converter counts: shared ontology infrastructure versus deliberately fixture-scoped pipeline. The root README's generic bidirectional responsibility does not override actual Palantir import-only and RelationalAI export-only code.
- Round-trip fidelity must distinguish portable semantics from native restoration: native snapshots/extensions in NVIDIA/Sigma/OBML can restore source detail that another Ossie consumer cannot execute. Official repository tests show intended contracts, not independent runtime certification in this investigation.
