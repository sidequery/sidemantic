# Warehouse converter comparison

## Coverage matrix

| Spoke | Official actual behavior | Local actual equivalent | Result |
|---|---|---|---|
| Snowflake | Offline Ossie → Cortex Analyst YAML only | `SnowflakeAdapter` imports and exports Cortex YAML | Local broader directionality and Cortex metadata, but major key/type losses |

## Snowflake

Official entry point validates exact Ossie version `0.2.0.dev0`, flat root, rejects `semantic_model` wrappers and removed root dialect/vendor lists. It selects SNOWFLAKE then ANSI_SQL then OSSIE_SQL_2026 expressions; unsupported-only expressions are skipped with warnings. No SQL transpilation in expression selection. [Source](https://github.com/apache/ossie-converters/blob/011ea9f9a1e2c941f351e18e071622339ccae881/snowflake/src/ossie_snowflake/ossie_to_snowflake.py#L82), [dialect selection](https://github.com/apache/ossie-converters/blob/011ea9f9a1e2c941f351e18e071622339ccae881/snowflake/src/ossie_snowflake/ossie_to_snowflake.py#L378).

Official preserves all composite primary-key columns and unique keys (omitting a unique key identical to PK), all relationship column pairs, scalar logical types, distinction between field dimension role and datatype, temporal type precision distinctions (Date/DateTime/DateTimeTz), synonyms/descriptions, and root metrics. Sources accept fully qualified quoted/unquoted names or SELECT/WITH encoded as `base_table.definition`. [Dataset conversion](https://github.com/apache/ossie-converters/blob/011ea9f9a1e2c941f351e18e071622339ccae881/snowflake/src/ossie_snowflake/ossie_to_snowflake.py#L183), [relationships](https://github.com/apache/ossie-converters/blob/011ea9f9a1e2c941f351e18e071622339ccae881/snowflake/src/ossie_snowflake/ossie_to_snowflake.py#L335), [source parsing](https://github.com/apache/ossie-converters/blob/011ea9f9a1e2c941f351e18e071622339ccae881/snowflake/src/ossie_snowflake/ossie_to_snowflake.py#L489).

Official losses: labels, custom extensions, structured AI context other than consumed synonyms; relationship AI context; metric datatype. **Dataset-scoped metrics are silently ignored**: `_convert_dataset` processes fields only; root `_convert_model` processes metrics. Confirmed in executable probe, no warning. This is a specific upstream weakness relative to the local Cortex adapter, which parses table metrics and root metrics. The official converter has no Snowflake importer despite other documentation elsewhere discussing eventual reverse conversion.

Local strengths: bidirectional facts/legacy measures, table and graph metrics, segments↔filters, synonyms/sample values, private access, nested Cortex search services, non-additive dimensions, relationship names referenced by `using_relationships`, labels/tags, verified queries, custom/module instructions. Selected metadata survives native serialization. [Field metadata](/workspace/sidemantic/sidemantic/adapters/snowflake.py:511), [top-level sections](/workspace/sidemantic/sidemantic/adapters/snowflake.py:537), [export metadata](/workspace/sidemantic/sidemantic/adapters/snowflake.py:785).

Local losses/compatibility concerns, confirmed by source:

- Composite PK reduces to first column; omitted PK becomes invented `id`. No dataset unique-key preservation. [Parsing](/workspace/sidemantic/sidemantic/adapters/snowflake.py:269). Tests explicitly assert this truncation [test](/workspace/sidemantic/tests/adapters/snowflake/test_parsing.py:234).
- Composite relationship retains first pair only; export forces `left_outer`. [Parsing](/workspace/sidemantic/sidemantic/adapters/snowflake.py:684), [export](/workspace/sidemantic/sidemantic/adapters/snowflake.py:1121).
- **Official `Integer` → `NUMBER(38,0)` is misread as categorical and re-exported as TEXT.** Parser recognizes exact `NUMBER`, `INT`, `INTEGER`, etc., not parameterized NUMBER/DECIMAL. It also reduces temporal exports to TIMESTAMP and fact types to NUMBER. [Type parsing](/workspace/sidemantic/sidemantic/adapters/snowflake.py:331), [exports](/workspace/sidemantic/sidemantic/adapters/snowflake.py:917).
- Model name becomes output filename stem; root description is not emitted. `base_table.definition` has no local parse path (`database/schema/table` only), so official subquery-backed source loses source SQL. [Table parsing](/workspace/sidemantic/sidemantic/adapters/snowflake.py:256), [root export](/workspace/sidemantic/sidemantic/adapters/snowflake.py:740).

Executable probe: minimal flat Ossie with Integer dimensions, composite PK `[tenant_id,id]`, unique key `[id,sku]`, dataset metric COUNT(*). Official output had two NUMBER(38,0) dimensions and full keys but no dataset metric, warnings `[]`. Feeding that YAML through local Snowflake parse/export produced TEXT dimensions, only tenant_id PK, no unique keys. This demonstrates actual cross-converter interoperability loss, not just differing feature lists.

## Databricks

[Official README](https://github.com/apache/ossie-converters/blob/011ea9f9a1e2c941f351e18e071622339ccae881/databricks/java/README.md) and source show pure text conversion, not a Databricks API connector. Ossie export chooses a fact/source, builds nested joins from graph, flattens dimensions with full join-path qualification, maps metrics→measures, labels→display_name, descriptions→comment, synonyms; key coverage informs `rely.at_most_one_match`. Import recovers datasets/relationships/fields/metrics and stashes known Metric View-only features under DATABRICKS custom extensions (filter/parameters/materialization; column format; measure window/partition/display_name; join rely/cardinality/on details). [Stash keys](https://github.com/apache/ossie-converters/blob/011ea9f9a1e2c941f351e18e071622339ccae881/databricks/java/src/main/java/org/apache/ossie/converter/databricks/MetricViewToOssie.java#L69).

Import conservatively labels expressions OSSIE_SQL_2026/ANSI_SQL/DATABRICKS. Filtered/windowed/partitioned measures stay DATABRICKS because interpreting only the portable expression without vendor stash would change value. [Semantic guard](https://github.com/apache/ossie-converters/blob/011ea9f9a1e2c941f351e18e071622339ccae881/databricks/java/src/main/java/org/apache/ossie/converter/databricks/MetricViewToOssie.java#L531). This is a useful pattern to reuse: retained vendor metadata does not equal executable portable semantics.

Limitations: exact Metric View 1.1/Ossie 0.2.0.dev0; acyclic connected graph resolvable to fact (or explicit source); 200-dataset/join-node cap; simple equi-joins only on import, rejecting cross/non-equi/function-wrapped/extra-filter joins; strict JSON stash and duplicate YAML-key rejection. Export drops logical datatypes, time role, non-synonym AI context, foreign vendor extensions with notices. Diamond datasets expand to aliased paths but ambiguous metric paths get dropped. [Export implementation](https://github.com/apache/ossie-converters/blob/011ea9f9a1e2c941f351e18e071622339ccae881/databricks/java/src/main/java/org/apache/ossie/converter/databricks/OssieToMetricView.java#L119), [drop notices](https://github.com/apache/ossie-converters/blob/011ea9f9a1e2c941f351e18e071622339ccae881/databricks/java/src/main/java/org/apache/ossie/converter/databricks/OssieToMetricView.java#L1200).

Do not repeat README's blanket “lossless” as universal: it applies to supported MV→Ossie→MV shapes; stash is a list of recognized keys, inputs are rejected in several cases, and Ossie→MV→Ossie discards declared semantics.

## BigQuery (really LookML)

Official output includes views **and explores with transitive joins**; local LookML export emits `data = {"views": views}` and no explores/relationships. Local import is much broader and bidirectional, while official BigQuery has no reverse importer. [Local export](/workspace/sidemantic/sidemantic/adapters/lookml.py:4076), [official planning](https://github.com/apache/ossie-converters/blob/011ea9f9a1e2c941f351e18e071622339ccae881/bigquery/src/ossie_bigquery/ossie_to_lookml.py#L153), [official explores](https://github.com/apache/ossie-converters/blob/011ea9f9a1e2c941f351e18e071622339ccae881/bigquery/src/ossie_bigquery/ossie_to_lookml.py#L1103).

Official strongest features: BIGQUERY→ANSI_SQL→OSSIE_SQL_2026 selection with sqlglot conversion into BigQuery dialect; logical types/date groups and timezone distinction; collision-aware names and timeframe expansion; composite PK hidden dimensions; root and dataset-scoped metric ownership resolution; filtered aggregate rewriting; compound aggregate helper measures preserving Looker's symmetric aggregation; composite joins, aliases, transitive explore paths. [Metric planning](https://github.com/apache/ossie-converters/blob/011ea9f9a1e2c941f351e18e071622339ccae881/bigquery/src/ossie_bigquery/ossie_to_lookml.py#L802), [full mapping and caveats](https://github.com/apache/ossie-converters/blob/011ea9f9a1e2c941f351e18e071622339ccae881/bigquery/README.md).

Official limitations: produces one document requiring split into model/view files plus connection/include; assumes many_to_one left_outer; diamond paths/cycles skipped with warnings; window/non-native aggregates emitted with warnings and may need manual rewrite; drops unique keys/extensions/metric datatype and unsupported AI context. Local already preserves LookML styling metadata like value formats/group labels/tags and handles broader LookML input; do not characterize official as a wholesale replacement. Highest-value local borrowing is explore/relationship export and BigQuery-specific dialect/type handling.

## Polaris

Official imports namespace→one flat Ossie document per nonempty namespace, tables→datasets, schema fields→typed ANSI_SQL expressions, identifier IDs→PK, timestamps→time role, exact Iceberg types and table properties→POLARIS custom extension. Exports model→namespace and datasets→empty Iceberg tables, source→ossie.source property, descriptions→comments, keys→identifier IDs. [Importer](https://github.com/apache/ossie-converters/blob/011ea9f9a1e2c941f351e18e071622339ccae881/polaris/src/main/java/org/apache/ossie/converter/polaris/PolarisImporter.java#L60), [export creates tables](https://github.com/apache/ossie-converters/blob/011ea9f9a1e2c941f351e18e071622339ccae881/polaris/src/main/java/org/apache/ossie/converter/polaris/PolarisExporter.java#L61).

Crucial limitation: no `/semantic-models` API; metrics/relationships/AI context/computed expressions are not written and trigger warnings. Exact extension type first, then datatype, legacy hint, time role, name heuristics, default string. Decimal defaults to decimal(18,2) with warning; opaque needs extension for exact recovery. Export type details and nested IDs reconstructed, not data moved. [Loss warnings](https://github.com/apache/ossie-converters/blob/011ea9f9a1e2c941f351e18e071622339ccae881/polaris/src/main/java/org/apache/ossie/converter/polaris/PolarisExporter.java#L90), [README mapping](https://github.com/apache/ossie-converters/blob/011ea9f9a1e2c941f351e18e071622339ccae881/polaris/README.md).

Schema nuance: parser rejects wrapper/removed root dialect/vendor fields and requires string version/name + list datasets, but does **not** enforce a version allowlist there (unlike Snowflake/BigQuery/Databricks). Importer emits 0.2.0.dev0. [Parser](https://github.com/apache/ossie-converters/blob/011ea9f9a1e2c941f351e18e071622339ccae881/polaris/src/main/java/org/apache/ossie/converter/polaris/OssieModelParser.java#L58).
